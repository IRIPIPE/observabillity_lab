# Разборы учебных инцидентов

Сценарии ниже были выполнены в ходе лабораторной. Перед новыми экспериментами
следует запустить основной стенд. Искусственную SQL-задержку и demo-алерты
после проверки отключать.

## 1. API остановлен

- **Воздействие:** `docker compose stop api`.
- **Симптом:** запросы к API не проходят, target `task-api` переходит в DOWN.
- **Обнаружение:** `up{job="task-api"}` становится 0; `TaskApiScrapeDown`
  проходит Pending → Firing после сохранения условия 30 секунд.
- **Доставка:** webhook получает JSON со статусом `firing`.
- **Восстановление:** `docker compose start api`, успешный scrape,
  затем уведомление `resolved`.
- **Вывод:** алерт обнаруживает недоступность сбора метрик; он не проверяет
  работоспособность каждой функции API.

## 2. БД недоступна, API продолжает работать

- **Воздействие:** остановка `db` во время потока запросов к `/tasks`.
- **Симптом:** `/tasks` возвращает 503 с `Database unavailable`,
  `/metrics` доступен, `up` API остаётся 1.
- **Обнаружение:** растёт Counter с `outcome="error"`, доля ошибок
  на дашборде достигает 100% в окнах без успешных запросов.
- **Алерт:** при доле >20% и трафике >1 запроса/с в течение 30 секунд
  срабатывает `TaskApiHighErrorRate`; доставка `firing` подтверждена.
- **Восстановление:** запуск `db`, продолжение успешных запросов,
  падение доли ошибок и получение `resolved` подтверждены.
- **Вывод:** работающий процесс и успешный scrape не означают успешные
  пользовательские операции. Одного `resolved` недостаточно для доказательства
  восстановления: условие также перестаёт выполняться при низком трафике.

## 3. Медленные успешные ответы

- **Воздействие:** временный `cursor.execute("SELECT pg_sleep(2)")`
  перед чтением списка задач и пересборка API.
- **Симптом:** запросы успешны, но средняя длительность около 2 секунд.
- **Обнаружение:** повышаются Histogram duration и Gauge in-progress;
  при потоке около 4 запросов/с наблюдалось примерно 8 занятых обработчиков.
- **Алерт:** `TaskApiHighLatency` сработал, webhook получил `firing`.
  Уведомление `resolved` после эксперимента также получено.
- **Восстановление:** удалить `pg_sleep`, пересобрать API, проверить быстрые
  успешные ответы при продолжающемся трафике.
- **Вывод:** корзина 2–5 секунд даёт оценку p95 около 4,85 секунды, когда
  наблюдения лишь немного превышают 2 секунды. Это ограничение точности
  Histogram, а не доказательство отдельных запросов длительностью 4,85 секунды.

## 4. Gauge не сохраняет историю коротких событий

- **Воздействие:** три параллельных запроса с временной SQL-задержкой.
- **Наблюдение:** прямое чтение `/metrics` показало in-progress 3, затем 0.
- **Объяснение:** scrape раз в 5 секунд может не застать короткие обращения.
  Counter сохранит накопленный прирост, но Gauge отражает только состояние
  на момент чтения. `finally` уменьшает Gauge и при ошибке обработчика.
- **Вывод:** отсутствие пика Gauge не доказывает отсутствие параллелизма.

## 5. Группировка, маршрутизация и inhibition

- **Стенд:** искусственные алерты с `job="routing-demo"`; без остановки сервисов.
- **Группировка:** `LabHighLatency` и `LabHighErrors` уровня warning
  объединяются по `job` и направляются в `lab`.
- **Маршрутизация:** критический `LabServiceDown` направляется в `lab-critical`.
  Оба receiver используют один webhook, но поле `receiver` позволяет
  различать маршруты.
- **Inhibition:** наличие критического источника подавляет уведомления
  о warning-алертах с таким же `job`; их состояние в Prometheus остаётся Firing.
- **Silence:** отдельно проверялось временное подавление по matchers;
  оно не устраняет исходную проблему.
- **Текущее состояние:** все demo-правила отключены выражением `vector(0) == 1`.
